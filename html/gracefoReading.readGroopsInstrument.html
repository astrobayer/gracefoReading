gracefoReading.readGroopsInstrument

Read a GROOPS ASCII instrument file.

Syntax

[time, data, info] = gracefoReading.readGroopsInstrument(fileName)
[time, data, info] = gracefoReading.readGroopsInstrument(fileName, ...
Name, Value)

Description

Reads an ASCII instrument file in the convention written by gracefoReading.writeGroopsInstrument: a version line, a two-integer type and dimension header, a lone record count and one record per line starting with the decimal MJD. It is the counterpart of the writer and serves two purposes: roundtrip verification of the export, and reading GROOPS-produced series back into MATLAB for comparison with Level-1B data.

The decimal-MJD time tag is recovered from the DIGITS of the record line, not from the double that sscanf would return. The integer and fractional parts are split at the decimal point and converted with int64 arithmetic, so the epoch is exact to every digit the file prints. Reading the same token through a double loses the low digits: a double holds MJD 58849 to an ulp of 0.63 microseconds, and over 200 000 epochs of 2020-01-01 the double path misplaced them by up to 314 ns while the digit path was exact. That is why 'TimeFormat', "gpsns" is offered here at all - it would otherwise return nine digits of which three are noise.

Accuracy and Limitations

  • Time is exact with respect to what the file prints. It is NOT exact with respect to a series that went through the writer: writeGroopsInstrument forms the decimal MJD as a double before printing it, so a write-then-read roundtrip is limited to about 0.6 microseconds by the writer, not by this reader. Only a file whose digits carry true sub-microsecond information delivers it.
  • At most the first 15 fractional digits are used. The 15th digit of a day is 86 picoseconds, so this cannot affect a nanosecond result; digits beyond it are discarded rather than rounded.
  • Rounding the fractional digits to whole nanoseconds can reach a full day (a tag within about 43 ps of midnight). The carry into the MJD column is applied, so seconds of day stays in [0, 86400).
  • Time tags must be plain fixed-point decimals. An exponential tag such as 5.8849e4 raises badTimeToken rather than being read through a double, because the digit path is what makes the nanosecond output meaningful. A sign is accepted only as '+': MJD is positive for every real epoch, and a negative tag would need floor semantics the integer split does not implement.
  • Time tags are validated before the declared column count, so a malformed tag raises badTimeToken and not countMismatch. The other order names the wrong cause: a tag like "58849.5.5" makes sscanf return three values where two columns were declared, and the reader would report a count error for a time problem.
  • Only the ASCII instrument format is read; GROOPS binary files are not supported.
  • Declared record and column counts are enforced, which catches truncated files, but the type code is not interpreted: the function does not know what the columns mean. Consult the GROOPS documentation of the type code in info.
  • Header conventions have not been verified against a specific GROOPS installation (see writeGroopsInstrument limitations); files from a real installation may carry additional comment lines, which this reader does not expect. It is therefore NOT established that this function reads the TU Graz operational orbit products - see obligation O-8 in HANDOVER.md.

Examples

roundtrip check of the exporter

gracefoReading.writeGroopsInstrument('acc.txt', t, acc);
[t2, acc2, info] = gracefoReading.readGroopsInstrument('acc.txt');
fprintf('max |dt| = %.3g s\n', ...
   max(abs((t2(:,1)-t(:,1))*86400 + t2(:,2)-t(:,2))));

compare a GROOPS-processed series with Level-1B data

[tg, dg] = gracefoReading.readGroopsInstrument('fromGroops.txt');
[tl, obs] = gracefoReading.readL1b('ACT1B_2020-01-01_C_04.txt');

exact int64 nanoseconds, for a lossless handoff

[tns, dg] = gracefoReading.readGroopsInstrument('fromGroops.txt', ...
   'TimeFormat', 'gpsns');
